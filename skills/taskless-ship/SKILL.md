# Сдача: PR, проверки, закрытие

Как довести проверенную работу до мержа и закрыть задачу по факту, а не по намерению.

## 1. Одна задача — одна ветка — один PR

Не смешивай в PR несколько задач: ревью читается по одной задаче, и откатить потом можно ровно её. Перед PR убедись, что проверки из `taskless-check` пройдены и доказательства лежат в критериях.

## 2. Ссылка на задачу — первой строкой

Первая строка описания PR — ссылка на задачу. Адрес бери из `get_task` (поле `url`), а не собирай руками: у воркспейсов со своим доменом он другой.

## 3. Слаг — в заголовке и коммитах

Слаг задачи (`PROJ-42`) ставь в заголовок PR и в коммиты. У проекта свой формат — он главнее: слаг идёт трейлером или в описание PR, не ломая формат.

## 4. Что писать в описании

- что сделано — коротко, по делу;
- чем проверено — доказательства из `taskless-check`: команды и их итог, скрины;
- развилки — где было два толкования и какое выбрано;
- что сознательно не сделано и почему.

## 5. Копия спеки

Первая подзадача эпика со спекой кладёт в этот же PR копию спеки: путь и шапку даёт `save_spec` (как — в `taskless-shape`). Следующие подзадачи обновляют копию, если документ менялся: выгрузи текущую версию (`export_document` в markdown) по тому же пути. Руками копию не правят; конфликт в этом файле решает новая выгрузка из документа. Проект сам задал место для спек — клади туда.

## 6. Ждать обязательных проверок

Жди, пока позеленеют обязательные проверки CI. Отметка GitHub «можно мержить» появляется раньше, чем проверки успевают прицепиться к PR, поэтому она ничего не доказывает. Какие проверки обязательные, смотри в настройках защиты ветки или в правилах проекта. Упала проверка — разберись и почини, а не перезапускай до зелёного.

## 7. Кто мержит

Мержит тот, кому проект это разрешает. Нет такого права — оставь PR готовым и скажи человеку. Есть у проекта гейт ревью — без вердикта не мержи, даже если CI зелёный.

## 8. Закрыть задачу после мержа

`finish_task` — после мержа, не раньше: задача закрывается по факту, а не по намерению. Релиз проекта может закрывать задачи по слагам из коммитов, поэтому не упоминай в коммитах чужие и будущие слаги — иначе релиз закроет то, что ещё не сделано. После мержа убери рабочую ветку и рабочую копию, если заводил их.
